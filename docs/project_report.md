## 1. Introduction

This report documents the design and implementation of a compiler front-end for a custom mini programming language, built as the Compiler Construction Lab course project. The compiler demonstrates all major phases of compiler construction: lexical analysis, syntax analysis, AST construction, symbol table management, semantic analysis, and intermediate code generation.

The project uses the standard compiler construction toolchain: **Flex** for lexical analysis, **Bison** for parsing, and **C** for all compiler logic. As a bonus, a **web-based GUI** was implemented to provide an interactive demonstration interface.

## 3. Language Specification

### 3.1 Data Types

| Type | Description |
|------|-------------|
| `int` | Signed 32-bit integer |
| `float` | Double-precision floating point |
| `bool` | Boolean: `true` or `false` |

### 3.2 Statements

- Variable declaration: `int x;`
- Assignment: `x = 5;`
- If statement: `if (cond) { ... }`
- If-else: `if (cond) { ... } else { ... }`
- While loop: `while (cond) { ... }`
- Print: `print x;`
- Nested blocks with scoping

### 3.3 Operators

| Category | Operators |
|----------|-----------|
| Arithmetic | `+  -  *  /  %` |
| Relational | `<  >  <=  >=  ==  !=` |
| Logical | `&&  ||  !` |

### 3.4 Context-Free Grammar (CFG)

```
program        → stmt_list

stmt_list      → stmt_list stmt
               | ε

stmt           → decl | assign | if_stmt | while_stmt | print_stmt | block

decl           → type_spec IDENT ';'

type_spec      → 'int' | 'float' | 'bool'

assign         → IDENT '=' expr ';'

if_stmt        → 'if' '(' expr ')' block
               | 'if' '(' expr ')' block 'else' block

while_stmt     → 'while' '(' expr ')' block

print_stmt     → 'print' IDENT ';'

block          → '{' stmt_list '}'

expr           → expr '+' expr | expr '-' expr | expr '*' expr
               | expr '/' expr | expr '%' expr
               | expr '<' expr | expr '>' expr | expr '<=' expr
               | expr '>=' expr | expr '==' expr | expr '!=' expr
               | expr '&&' expr | expr '||' expr
               | '!' expr | '-' expr
               | '(' expr ')'
               | IDENT | INT_LIT | FLOAT_LIT | BOOL_LIT
```

**Operator precedence (low → high):** `||` < `&&` < `== !=` < `< > <= >=` < `+ -` < `* / %` < `! unary-`

## 4. Compiler Architecture

The compiler pipeline flows as follows:

```
Source File → Lexer → Token Stream → Parser → AST
                                              ↓
                                       Symbol Table
                                              ↓
                                     Semantic Analyzer
                                              ↓
                                       TAC Generator
                                              ↓
                                    Three Address Code
```

All phases after the lexer are implemented inside `parser.y`.

---

## 5. Lexer Design (`src/lexer/lexer.l`)

The lexer uses Flex regular expressions to recognize tokens. Key design decisions:

- **Keyword-before-identifier ordering**: Keywords (`int`, `float`, etc.) are listed before the identifier rule so Flex matches `int` as a keyword, not an identifier.
- **Longest-match rule**: Flex automatically applies longest-match, so `<=` is matched before `<`.
- **Line tracking**: The `%option yylineno` directive makes Flex track line numbers automatically via `yylineno`.
- **Comment discarding**: Both `//` and `/* */` comments are silently consumed.
- **Invalid token reporting**: The catch-all `.` rule reports any unrecognized character as a lexical error.

---

## 6. Parser Design (`src/parser/parser.y`)

The parser is a LALR(1) parser generated by Bison.

- **Grammar**: The CFG from Section 3.4 is implemented directly as Bison rules.
- **Operator precedence**: Handled via `%left` and `%right` directives. No grammar ambiguity remains.
- **Error recovery**: The `error T_SEMI` rule allows the parser to skip to the next `;` after a syntax error, enabling multiple errors to be reported per run.

## 7. Abstract Syntax Tree

### Node Structure

Each AST node is a C struct with:
- `type`: what kind of node (from the `NodeType` enum)
- `data_type`: inferred type (`int`/`float`/`bool`)
- `op`: operator string for binary/unary nodes
- `name`: identifier name or type keyword
- `ival`/`fval`/`bval`: literal values
- `line`: source line number
- `child[3]`: up to 3 child pointers

### Construction Strategy

Nodes are built bottom-up during parsing. Each Bison grammar action calls `make_node()` to create a node and assigns children from sub-rule values (`$1`, `$2`, etc.).

### Visualization

The AST is printed as indented text: 2 spaces per depth level. Example:

```
Program
  Declare [int x] at line 1
  While at line 3
    Condition:
      BinaryOp [>] (type: bool)
        Identifier [x] (type: int)
        IntLiteral [0]
    Body:
      Assign [y =] at line 4
        BinaryOp [+] (type: int)
```

## 8. Symbol Table

### Data Structure

A **scoped stack** of fixed-size arrays. Each element of the stack represents one scope (one `{ }` block).

```
scope_stack[0]  (global scope)
scope_stack[1]  (first nested block)
scope_stack[2]  (second nested block)
...
scope_top       (index of current scope)
```

Each scope holds up to 256 `SymbolEntry` structs, each containing: name, type, line, used flag.

### Operations

| Operation | Implementation |
|-----------|---------------|
| `enter_scope()` | `scope_top++`, zero-initialize new scope |
| `exit_scope()` | `scope_top--`, variables go out of scope |
| `declare_var(name, type, line)` | Insert into `scope_stack[scope_top]`; error if duplicate |
| `lookup_var(name)` | Search from `scope_top` down to 0; return first match |

### Explanation (for teacher)

"Imagine a stack of notebooks. Each `{` opens a new notebook. Each `}` closes and discards it. Declaring a variable writes it into the current notebook. Looking up a variable searches from newest to oldest notebook."

## 9. Semantic Analysis

The semantic analyzer is integrated into `gen_code()`, a recursive function that walks the AST.

### Errors Detected

| Error | Detection Method |
|-------|-----------------|
| Undeclared variable | `lookup_var()` returns NULL |
| Redeclaration | `declare_var()` finds duplicate in current scope |
| Type mismatch in assignment | Compare declared type with inferred rhs type |
| Type mismatch in expressions | `binop_result_type()` returns `TYPE_UNKNOWN` |
| Invalid logical operands | Check `&&`/`\|\|` operands are `bool` |
| `!` on non-bool | Check unary `!` operand is `bool` |

Every error includes the line number and a descriptive message.

## 10. Intermediate Code Generation

### Three Address Code (TAC)

TAC instructions generated for each construct:

**Assignment:**
```
x = 5
```

**Binary expression:**
```
t1 = b * 2
t2 = a + t1
c = t2
```

**While loop:**
```
L0:
  t1 = x > 0
  if_false t1 goto L1
  ; body
  goto L0
L1:
```

**If-else:**
```
  t1 = flag == true
  if_false t1 goto L0
  ; then body
  goto L1
L0:
  ; else body
L1:
```

### Naming Conventions

- Temporary variables: `t1`, `t2`, `t3`, ... (global counter)
- Labels: `L0`, `L1`, `L2`, ... (global counter)

## 13. Conclusion

This project successfully implements a complete compiler front-end demonstrating all six required phases. The key insight is that a real compiler is just these phases chained together: the lexer feeds tokens to the parser, the parser builds a tree, and the tree is walked twice — once for semantic checks and once for code generation.

The simplest possible data structures were chosen deliberately: a flat array stack for the symbol table, C structs with 3 child pointers for the AST, and string arrays for TAC. These choices make every component easy to explain, trace, and verify.
